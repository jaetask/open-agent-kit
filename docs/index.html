Architecture · design draft · @jaetask/open-agent-kit, "Kit" for short

Standalone apps on pi-durable, joined by MCP and cards

Each app is one container with its own agent, actions, cards and MCP endpoint. Run one alone, or connect several into one experience.

From a single ideaEvery caller (UI, agent, another app, CLI) reaches a domain through one Call pipeline. Everything else is an adapter around that.
Three seamsThe agent runtime, identity, and where actions live (local or remote). Each has two real adapters from day one.
Answers to the hard problemsSmall interfaces, visible state machines, no remote code execution, and a stated answer for each hard problem.
1 · Ubiquitous language

The glossary

This is the project's GLOSSARY.md, in Matt Pocock's format: one meaning per term, plus the words we don't use. Code, docs, tests and UI all use these names. Architecture words (module, interface, seam, adapter, depth) keep his definitions, and machina keeps its own (MachineDefinition, Instance).

2 · The shape

One deep module, three seams, thin adapters

Callers on the left never touch a domain directly. They hand a Call to the pipeline. The pipeline needs three things from outside, each behind a small interface. Dependencies point inward only: a Domain imports nothing from pi-durable, MCP, HTTP or React.

The deletion test

Delete the pipeline and validation, authorisation, gating, audit and dedupe reappear in four callers. Delete a caller adapter and nothing else changes.

The interface is the test surface

Tests call invoke() and assert on the result. Nothing reaches past it, and nothing needs a model, a network or pi-durable.

One package, four entry points

One npm package, @jaetask/open-agent-kit. The root is the core (pipeline, domains, seams). Adapters are subpaths with optional peer dependencies: /pi (runtime adapter), /mcp (server and plugin client), /react (cards and chat). This page calls them kit, kit-pi, kit-mcp and kit-react for short. Plus machina.

What Kit does not handle

Your database schema, your UI framework, organisations and roles, multi-node scale-out. An app brings its own repositories behind its own Domain.

3 · Actions

One Action definition for every caller

One Action definition serves every caller: the UI, the agent, another app and the CLI. Each Action states what it does to the world once, as an Effect, and parallelism, crash safety, the Gate, audit and change events are derived from it.

// domains/tasks/actions/create-task.ts
export const createTask = defineAction({
  name: "create-task",
  description: "Create a task on the task list.",
  effect: "write",
  input: z.object({ title: z.string().min(1) }),
  output: Task,
  card: changed("created", "task"),
  run: ({ title }, { principal, tasks }) =>
    tasks.create({ owner: principal.id, title }),
});
// domains/tasks/domain.ts
export const tasksDomain = defineDomain({
  name: "tasks",
  version: "1.0.0",
  about: "Tasks, projects and due dates.",
  actions: [listTasks, createTask, deleteTask],
  cards: [taskList],
  // what run() receives besides the Principal
  provide: (app) => ({ tasks: app.repos.tasks }),
});
// The Contract is generated from this. Nobody writes one.

run() accepts its dependencies and returns a value. It never sees a request, a model, pi-durable or MCP, so a Domain is testable with plain function calls. An Action has seven fields.

4 · The Call pipeline

One state machine for every Call

The life of a Call is a machina MachineDefinition. The pipeline is its only driver, each Call is an Instance, and the machina visualizer shows any live Call in development. Step through it here: pick an event to send.

// The whole interface of the deep module.
interface Calls {
  invoke(call: Call, decision?: "yes"): Promise<Outcome>;
  decide(id: CallId, decision: Decision): Promise<Outcome>;
}
type Call = {
  id: CallId;              // chosen by the caller: the dedupe key
  action: ActionName;      // "tasks.create-task"
  input: unknown;
  principal: Principal;
  caller: "ui" | "agent" | "plugin" | "cli";
};
type Outcome =
  | { state: "succeeded"; output: Json; card?: CardView;
      changes: Change[] }
  | { state: "held"; hold: Hold }          // waiting for a Decision
  | { state: "rejected" | "declined" | "expired"
           | "failed" | "interrupted";
      reason: Reason };                      // errors are values
// Same Call id invoked twice returns the stored Outcome.
// The Outcome commits in the same transaction as the
// Domain's change, so a write to the App's database
// happens once, even across a crash.
5 · The seams

Three interfaces

pi-durable is experimental and changes between releases, so nothing outside kit-pi (the /pi entry point) may import it. The adapter is the only file set that moves when it changes, and the same conformance tests run against the fake and the real runtime.

// Seam 1. Adapters: kit-pi (pi-durable), fake (tests).
interface AgentRuntime {
  start(actions: ActionSource): Promise<void>;
  submit(to: ConversationId, input: Input,
         as: Principal): Promise<RunId>;
  watch(c: ConversationId,
        on: (view: ConversationView) => void): Unwatch;
  resume(call: CallId, outcome: Outcome): Promise<void>;
  stop(c: ConversationId): Promise<void>;
  close(): Promise<void>;
}
// Seam 2. Adapters: browser session, connection token.
interface Identity {
  authenticate(credentials: Credentials):
    Promise<Principal | null>;
}

// Seam 3. Adapters: local Domain, remote Plugin (MCP).
interface ActionSource {
  contract(): Promise<Contract>;
  run(call: Call, decision?: "yes"): Promise<Outcome>;
}
6 · Apps together

A Plugin is a Domain seen from outside

In DDD terms a Domain's Contract is its published language. Another app that installs it gets a Plugin: the same Actions and Cards, run remotely. To the host's pipeline a remote Plugin and a local Domain are both just an ActionSource, so the agent, the gates and the cards treat them identically.

Contract

Generated from defineDomain() and served by the MCP endpoint as the resource open-agent-kit://contract/<domain>: Actions with Effects, Card specs, Domain version. Semver: removing an Action or changing its input is a major bump.

Cards, in three tiers

A JSON Card spec every host can draw, an optional React component compiled into trusted hosts, and text with a link as the floor. A remote app can send data, never code.

Connection

Made by pairing: the person approves in Tasks, Tasks mints a token scoped to them and to the Effects allowed. Tasks keeps only a hash of the token. Its lifecycle (pairing, connected, revoked) is a second MachineDefinition.

# docker-compose.yml: someone who wants Tasks and Talk
services:
  tasks:
    image: ghcr.io/…/tasks
    volumes: [tasks-data:/data]        # two SQLite files: app data and agent state
    ports: ["3120:3120"]               # UI + /mcp
  talk:
    image: ghcr.io/…/talk
    volumes: [talk-data:/data]
    ports: ["3911:3911"]
    environment:
      KIT_CONNECT: http://tasks:3120/mcp   # offers pairing on first start

8 · Build plan

Seven layers, each with a proof

The repository starts empty. A layer is done when its proof is committed and green and its interface is written down; only then does the next one start. Proofs are expect tests (@jaetask/snap): one input file per case, with a human-approved name.expect.md beside it, so every claim on this page ends up as a folder of readable Markdown. One small example Domain with a read, a write and a danger Action is carried through every layer, so no layer is proven only on paper.

Built on: pi-durable 1.5.2 (MIT), machina (MIT, core derived from Zag.js), Matt Pocock's codebase-design vocabulary and glossary format (github.com/mattpocock/skills), and what an earlier prototype of Talk on pi-durable already proved: one extension per app over MCP, a read/write/danger classifier, a durable danger gate and stored cards.

Inspired by agent-native's idea of one Action definition for every caller. The code is being added one layer at a time, each with its proof; see the build plan above.
